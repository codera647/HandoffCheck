# Implementation status

## Repeating approval reminders · 15 October 2026

Authors can save a per-request interval from 15 minutes to 7 days and choose in-app reminders plus optional email directly from their connected Gmail account. Settings can be prepared on a draft; the timer starts only when the current revision is ready for approval. Each cycle selects only current active pending leads. Partial approval preserves the remaining lead's timer; clarification, a new draft, completed approval, archive and pause suspend or stop it. A paused author setting suppresses the legacy one-time workspace default.

The signed minute scheduler detects due request schedules and mail retries. Private email slots use leases, frozen retry payloads, three attempts maximum and a 23-hour retry cutoff. Gmail has no send-idempotency contract: timeouts, HTTP 5xx and abandoned sending leases become delivery unknown without a same-cycle resend. A final gate checks approval, addresses, plan and connection version. New cycles replace old queued work instead of replaying missed reminders. Provider acceptance is shown separately from inbox delivery; no delivery/bounce webhook or desktop push is implemented. [Reminders.md](Reminders.md) documents the workflow, diagrams, permissions and Google setup.

The Gmail extension adds a separate consent flow with hashed single-use state, encrypted PKCE verifier, verified Google subject/email matching and an encrypted refresh token. Only the active author can start it; stale connection generations cannot finish or send. Disconnect clears stored credentials and queued author emails while preserving login and in-app schedules. The existing neutral sidebar shows sender metadata and author-only connection controls. Resend secrets are unused.

Local verification covers **86 application/provider/database tests**, TypeScript, both frozen Edge checks, the production build, all 15 browser workflows and seven native authentication tests. OAuth callback tests use synthetic Google/Auth transports; database cases cover state consumption, expiry, disconnect, stale generations and uncertain delivery. Browser checks cover author disconnect, failed connection, read-only leads and narrow layouts; screenshots were inspected. The existing initial-chunk warning remains.

The Gmail migration and both Edge Functions are deployed. Hosted metadata checks confirm RLS and denied client read/truncate privileges on credentials/state tables, service-only OAuth and delivery functions, and an authenticated disconnect restricted to the current account. Advisor warnings include intentional guarded SECURITY DEFINER RPCs and the existing leaked-password setting; this is not a full security audit. Live Gmail consent and inbox acceptance require the author; automated tests do not send real email.

## Available locally

The React app includes a requests table with search, filters and pagination, an assigned-review queue, a structured feature editor, clarification discussion, two-stage approval, revision comparison, saved briefs with Markdown download/copy/print, membership settings and checklist version publishing. The demo persists data and files in IndexedDB and labels simulated identities and checklist-only review.

Saving creates a new immutable revision. Approval requires an active assigned lead different from the author and applies to one reviewed revision and input hash. An approval confirmation captures that revision when opened. Requested changes require a new revision. Old approved briefs remain readable after edits. Brief generation is deterministic and one artifact is retained per revision.

The Supabase migrations implement the hosted transactions, read policies, invite acceptance, administrator controls, quota limits and private upload reservations. The Edge Function implements verified bearer authentication, the API routes used by the frontend, signature verification, signed downloads and optional Gemini structured review.

## Implementation choices

- Request pagination uses a stable sort by updated timestamp and number, with page offsets of 25. It does not use the proposed cursor API. At 10–20 pilot users this keeps the table simple; concurrent changes can move rows between pages.
- The initial checklist contains the approved mandatory baseline. Administrators can publish named versions; arbitrary checklist-field configuration is not included.
- File limits apply to retained uploads, including historical and failed reservations. Five active attachments alone would permit unbounded historical storage. Operator cleanup releases capacity.
- Demo and SQL workflows implement the same permission and state rules in their respective runtimes. Shared Zod contracts validate the API boundary; PostgreSQL independently enforces write rules. Tests cover revision hashing and representative workflows in both.
- The export templates have the same substantive sections. PostgreSQL uses plain reference text and bullet criteria; the browser demo uses Markdown links and numbered criteria. Each stored export has its own content hash.
- AI is optional. Checklist-only review reports field presence and does not claim to judge language ambiguity or implementation feasibility.
- Idempotent retries apply to request creation and workflow commands. Admin actions and upload reservations do not use command receipts; duplicate pending invitations are rejected, and unsuccessful upload reservations remain counted until cleanup.
